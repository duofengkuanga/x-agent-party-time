# 工程执行约定与 XHandoff 交接

## Problem Statement

开发负责人已经在工程内维护构建和部署入口，却仍需在平台环境配置里重复填写具体部署命令。平台保存和冻结这些命令，xapt 又识别后端准备参数、前端部署命令及其验证变体，使工程知识分散在平台、Runner、Skill 和工程文档之间。工程脚本变化时，多处规则可能失去一致性。

当前后端的部署入口只消费预先准备的 JAR，不会自动打包。准备命令由 XUpdate 按工程文档发现并执行，不是平台固定调度的步骤。界面只呈现部署命令，容易让使用者误以为构建已经包含在其中，也难以理解修复会话和更新会话分别构建什么、产物如何交接。

修复和更新已使用独立工作区，并通过 Repair Handoff 传递候选提交对应的技术上下文。现有交接规则仍附着在执行 Skill 中；缺少一个独立、共同版本化的 Skill 来集中定义交接的内容、引用、适用条件与诚实性边界。直接搬运完整聊天、临时交接文件或修复的构建目录，都不能替代可恢复、可核验的交付流程。

## Solution

平台只表达本次工作的业务目标：参与的 Engineering、Binding、目标分支、目标环境、Bug 与 Update Batch，以及执行状态和结果。环境配置不再要求填写具体构建、准备、部署或验证命令；工程相关流程集中到 x-skills 和各工程自己的文档。

XBugRepaire 和 XUpdate 都直接读取当前工程固定路径 `.xapt/README.md` 的工程执行约定，无需在 `AGENTS.md` 配置链接。约定说明运行条件、分阶段验证要求、构建入口、各环境部署与验收入口、缓存和产物归属，以及失败恢复方式。工程文档与代码一起版本管理，详细说明可链接已有文档，不创建与实际脚本重复的第二套流水线。

Repair Attempt 在自己的工作区修复和验证 Bug，按改动范围决定是否编译、测试或打包，默认不 Push、不部署。修复构建必须包含当前工作区的实际修改。Update Batch 在独立更新工作区集成全部冻结候选，检查最终组合，准备与最终已提交版本匹配的部署包；所需 Push 均确认成功后，再按目标环境约定部署同一产物并验收。

新增 XHandoff，集中定义结构化交接规则。XBugRepaire 在成功形成候选提交后按该 Skill 生成交接；平台将交接与来源提交、Repair Attempt 绑定并随批次冻结；XUpdate 读取并核实交接，使用有效的环境经验和文档引用继续工作。通用约定留在工程文档，本次运行事实留在 Repair Handoff，Schema 继续由平台契约拥有。

xapt 保留通用工作区、会话恢复、Skill Bundle、命令观察和结果校验能力，移除针对具体工程命令及参数的特殊识别。减少字段与工程知识不降低证据要求：采用的约定版本、环境、提交、实际命令及部署结果仍必须能够关联和核验。

## User Stories

1. 作为工程配置维护者，我希望在平台只维护环境身份和必要说明，以便不用重复填写仓库已有的命令。
2. 作为开发负责人，我希望构建和部署规则随工程代码管理，以便修改脚本时能同时维护其使用约定。
3. 作为开发负责人，我希望每个工程都有明确且唯一的执行约定入口，以便 Agent 不需要猜测该读哪个文档。
4. 作为开发负责人，我希望不同工程分别使用自己的运行时和工具，以便前端与后端不会互相套用执行方式。
5. 作为提测参与者，我希望环境选择能稳定对应工程约定，以便修改展示名称不会悄悄改变部署目标。
6. 作为开发负责人，我希望环境缺失或匹配有歧义时明确停止，以便 Agent 不猜测服务器、目录或命令。
7. 作为开发负责人，我希望 XBugRepaire 与 XUpdate 都读取当前工程约定，以便修复和交付遵守同一套规则。
8. 作为开发负责人，我希望约定明确列出 Docker、运行时、依赖和认证前置条件，以便执行前能发现缺项。
9. 作为开发负责人，我希望可安全解决的本机运行条件由执行会话按约定准备，以便减少重复人工操作。
10. 作为开发负责人，我希望认证信息留在本机或既有凭据机制中，以便平台和交接数据不保存密码或私钥。
11. 作为开发负责人，我希望修复只执行当前改动所需的检查，以便不为每条 Bug 提前做全部发布工作。
12. 作为开发负责人，我希望修复构建包含当前工作区尚未提交的修改，以便验证的确实是本次修复。
13. 作为开发负责人，我希望修复阶段清楚区分编译、打包和测试，以便跳过测试的打包不会被报告为测试通过。
14. 作为开发负责人，我希望修复会话默认只生成本地候选提交，以便不会提前 Push 或部署未集成的版本。
15. 作为开发负责人，我希望候选成功后形成有界交接，以便更新会话能继续使用已经确认的工作上下文。
16. 作为维护者，我希望 XHandoff 独立定义交接规则，以便两份执行 Skill 不各自维护一套相似说明。
17. 作为开发负责人，我希望交接引用提交、工程文档和代码位置，以便不复制容易过时的整份文档或 diff。
18. 作为开发负责人，我希望交接保留实际验证命令、运行条件与覆盖范围，以便更新会话理解之前检查证明了什么。
19. 作为开发负责人，我希望交接记录已经验证的环境解决办法及适用条件，以便更新会话不重复排查同一问题。
20. 作为开发负责人，我希望交接明确列出未完成事项和限制，以便更新会话不会将缺失信息当作成功。
21. 作为开发负责人，我希望交接能说明后续可能需要的 Skill 及原因，以便下一个会话知道可用的工作方法。
22. 作为开发负责人，我希望建议使用的 Skill 不改变已有授权或会话绑定，以便交接不能成为扩大权限或切换规则的入口。
23. 作为开发负责人，我希望交接说明产物对应的代码版本、输入和复用条件，以便不会把任意旧包作为部署包。
24. 作为开发负责人，我希望没有构建产物时不强行生成产物说明，以便不会为了填交接而增加无关构建。
25. 作为提测参与者，我希望交接随候选提交和批次保存，以便进程重启或临时文件清理后仍可恢复。
26. 作为开发负责人，我希望更新核对交接来源、候选提交和当前工程约定，以便历史信息失效时能被发现。
27. 作为开发负责人，我希望更新只补查缺失或失效的信息，以便不重复读取整段聊天和排查已解决的环境问题。
28. 作为开发负责人，我希望全部候选集成后再安排最终验证和部署包准备，以便不会逐个候选重复完整打包。
29. 作为开发负责人，我希望部署包明确绑定最终提交和相关构建输入，以便远端运行版本可以追溯。
30. 作为开发负责人，我希望工程已有的可靠产物缓存仍可使用，以便输入匹配时省去重复构建。
31. 作为开发负责人，我希望修复与更新的可写产物目录保持独立，以便并行执行不会相互覆盖。
32. 作为开发负责人，我希望文档区分依赖缓存与完整产物缓存，以便不会把依赖复用误认为修复包复用。
33. 作为开发负责人，我希望代码或相关输入变化后重新检查产物有效性，以便已经通过的历史结果不会掩盖新变化。
34. 作为开发负责人，我希望准备成功后先 Push，再部署准备好的同一个包，以便远端代码和部署产物一致。
35. 作为开发负责人，我希望部署入口不会无依据地重新打包，以便已经完成的准备不会被重复执行。
36. 作为开发负责人，我希望 84 和 85 的部署及验收方式在工程文档中分别明确，以便目标不会混淆。
37. 作为开发负责人，我希望缺少部署包时得到明确失败，以便部署入口不会猜选旧包或偷偷代替前置步骤。
38. 作为开发负责人，我希望平台依据真实命令结果和验收证据判断交付，以便模型的一句成功说明不能推进业务状态。
39. 作为开发负责人，我希望恢复时先读取远端实际版本和验收记录，以便不会盲目重复上传或重启。
40. 作为开发负责人，我希望多个工程分别解析自己的约定、执行自己的命令，以便一个会话不会把前后端的版本和证据混用。
41. 作为测试负责人，我希望只有本批所有必需部署成功后才进入待验证，以便面对完整的更新结果。
42. 作为开发负责人，我希望部分部署成功后保留真实现场和阶段结果，以便继续处理失败部分而不自动回滚成功部分。
43. 作为维护者，我希望 xapt 不内置工程名称、环境数字或脚本参数转换，以便新增工程不要求发布 Runner 特例。
44. 作为开发负责人，我希望 XHandoff 与两份执行 Skill 使用同一固定规则包，以便旧会话恢复时不会混用新旧交接规则。
45. 作为测试负责人，我希望继续看到业务结果和验证范围，以便技术交接细节不会淹没验收信息。
46. 作为开发负责人，我希望能查看必要的约定来源和技术执行证据，以便定位失败并核对交付版本。
47. 作为历史提测参与者，我希望契约切换保留旧记录的真实含义，以便旧命令配置不会被伪装成新约定下的部署证据。
48. 作为维护者，我希望验收覆盖真实 Codex 读取文档并执行完整链路，以便不把文案检查或手工运行脚本当作平台自动流程已经通过。

## Implementation Decisions

1. **业务目标与执行方法分开。** 平台保留工程、Binding、目标分支、目标环境、批次及业务状态，不再提供构建、准备、部署、验证命令的编辑字段。不能用新的高级配置表单重新引入相同职责。
2. **工程约定是工程相关执行方法的唯一来源。** 每个工程使用固定目录 `.xapt/`，以 `.xapt/README.md` 为唯一入口；通用读取规则集中在 XHandoff，无需新增或修改工程的 `AGENTS.md` 链接。入口包含交付配置，可按阶段引用已有详细文档。两份执行 Skill 都读取该入口；平台不复制文档全文，也不建设新的通用流水线编排器。
3. **明确环境身份与匹配规则。** 优先复用现有环境身份及必要的可读信息，形成与工程约定唯一、稳定的对应。缺失、重复或矛盾的映射阻止交付；不从环境数字猜测 IP、SSH 身份、端口或目录，也不要求 Server 保存本机地址和凭据。
4. **工程文档覆盖完整执行生命周期。** 至少包含运行条件及检查方式、修复验证、更新验证与准备、按环境部署、部署验收、依赖与产物缓存、失败恢复、资源清理和凭据边界。必须说明每个命令的输入、执行阶段、产物归属、成功条件及副作用。
5. **XBugRepaire 保留修复职责。** 在当前修复工作区完成问题调查、修改、适用检查、已有评审要求与候选提交。按修改范围执行必要构建，不为缩短 Update 时间强迫每个 Bug 提前完成全部发布检查；不因读到部署文档而获得 Push 或部署权限。
6. **修复构建与正式产物准备明确区分。** 修复检查必须验证当前工作区的真实修改，包括未提交内容；不能使用只检出旧提交的入口漏掉本次修改。正式部署产物针对更新工作区的最终已提交版本准备。工程现有入口不能满足这些语义时，实施应补齐最小必要支持，不能只写一份与脚本不符的文档。
7. **XUpdate 保留最终组合的验证责任。** 核对冻结批次和交接后，集成全部候选，再安排最终验证及产物准备。确认全部所需 Push 后才开始部署；工程相关准备和验收方式从对应工作区文档取得，不从平台命令字段取得。
8. **准备与部署复用同一可信产物。** 若工程支持预先准备产物，在最终输入上准备一次，Push 后部署同一产物。准备不包含的必需检查仍需执行。若工程实际必须重建，应明确记录原因与覆盖范围，不伪造跳过参数或重复构建已被消除的结论。
9. **共享依赖与隔离产物继续成立。** 不搬运或软链修复的可写构建目录到更新工作区。依赖缓存可以按工程约定共享；已有封存产物只有在工程入口证明输入匹配、产物完整和版本满足要求时才能复用。XHandoff 的描述本身不是缓存命中或免检凭证，本次不新建 xapt 通用产物仓库。
10. **抽出 XHandoff 的语义职责。** 集中规定交接应包含哪些已经确认的事实、如何引用既有材料、如何记录验证与产物条件、如何表达剩余事项和建议 Skill，以及哪些内容禁止传递。它不执行修复、构建、Push 或部署，也不替调用者返回另一份终态结果。
11. **保持结构化交接及契约所有权。** XBugRepaire 在候选成功后按 XHandoff 规则形成数据，XUpdate 按交接规则核实和使用。平台契约继续唯一拥有 Schema 和校验；规则包不复制独立 Schema。按实际需要扩展已有交接结构，不同时维护自由 Markdown 与结构化数据两套权威交接。
12. **交接按来源保存并冻结。** 交接与来源 Repair Attempt、Execution 和候选提交绑定，随批次原子冻结。无改动或失败结果不能冒充成功候选的交接。已有失败草稿和恢复机制继续使用原有事实记录，不通过本次重构丢弃。
13. **引用与本次事实分开。** 通用流程引用当前工程文档，修改内容引用候选提交和必要代码位置；本次交接记录实际执行、已验证的环境解决办法、影响范围和未完成事项。避免完整聊天、原始日志和重复 diff；使用可移植引用，不泄露本机绝对路径、身份信息或凭据。
14. **建议 Skill 不扩大执行权限。** 只记录与后续任务有关的建议和原因，按既有可用性与授权边界使用。XHandoff 本身作为两份执行 Skill 的固定配套规则交付，不能从交接文本任意下载、切换或执行其他 Skill。
15. **执行证据保持可核验。** 实际采用的工程约定版本、目标环境、最终提交、执行命令和部署结果必须相互对应。来源与版本绑定必须可核实，不能仅由模型自报。普通日志、伪造回执、其他环境或旧版本证据不能使批次成功。
16. **xapt 只保留通用技术机制。** 移除对具体部署命令、前后端脚本名称、环境编号及验证参数变体的硬编码。保留工作区身份、真实命令来源、进程退出、部署证据、会话恢复和结果一致性检查；具体工程的部署成功条件由工程入口实现并在约定中说明。
17. **恢复不依赖临时交接文件。** 通用 handoff Skill 的临时文档形式不作为平台持久化方式。中断或副作用结果未知时，先按已采用的工程约定核对现场，确认后从未完成阶段继续；输入或约定版本变化使不再适用的证据失效，不静默套用新命令。
18. **多工程语义保持不变。** PersonAgent 和 AgentParty 均使用工程约定；逐工程核对工作区、环境和结果。保留已有冻结范围、部署顺序、资源占用、全部所需 Push 后才部署、整批成功才待验证及部分成功不自动回滚的边界，不借本次调整重做业务调度。
19. **规则包一起分发并固定。** XHandoff 与 XBugRepaire、XUpdate 纳入同一代不可变 Skill Bundle。更新安装、完整性检查、初次调用与恢复都要覆盖配套规则；旧 Task 不解析到当前全局入口的最新 XHandoff。缺失配套规则应给出明确失败，不能静默混用版本。
20. **完整移除命令配置依赖。** 同步调整环境配置界面、工程契约、持久化、批次快照、Execution Brief、结果断言、技术投影及测试；不保留旧命令作为隐式 fallback。历史执行记录继续表达当时事实，不能作为新流程的执行依据。
21. **契约切换有明确边界。** 按开发期策略直接使用新契约，不增加长期双写或兼容运行分支。实施前盘点活动任务与固定规则包，制定可验证的切换方式；无法安全续接的任务明确阻塞，不静默换会话、改写冻结批次或清除历史。实际数据操作仍遵循既有授权边界。
22. **实施跨仓库协调。** 平台、x-skills、当前前端与后端工程共同完成切换。文档必须与实际脚本、运行环境和产物语义一致；真实部署账号配置属于本机认证工作，不把凭据搬入工程约定或平台。

## Testing Decisions

用户已确认：以现有“Repair → 冻结交接 → Update → 部署结果”的完整链路为主验收边界，补充真实工作区与真实 Codex 会话验证；远端使用隔离测试目标。

优先复用生产与场景测试共用的提测工作流装配、Agent 公开协议和现有临时 Git 工程。断言用户可观察行为、真实 Git 与产物事实、部署副作用及恢复结果，不以私有函数形状、提示词关键词或模型声称成功替代验收。不引入平行工作流测试框架。

1. **平台配置与业务回归。** 验证环境配置不再要求命令，环境选择和身份稳定，新增及更新工程配置、提测、批次冻结、角色投影均使用新契约；PersonAgent 和 AgentParty 的既有权限、范围和调度行为不变。
2. **工程约定发现。** 使用固定文件存在或缺失、缺少 AGENTS.md、AGENTS.md 含无关或旧链接、配置块重复、环境缺失或重复的工程夹具。验证前后端独立读取各自的 `.xapt/README.md`；失败发生在相关副作用之前，不能猜测环境或使用旧链接、旧平台命令。
3. **修复构建真实性。** 在真实临时 Git worktree 中保留未提交修复，运行工程规定的修复检查，证明构建包含修改而非旧 HEAD。验证仅必要检查会执行，修复不会 Push 或部署，并区分打包通过与测试通过。
4. **更新正式产物。** 集成多个候选后准备最终包，检查包中版本、构建输入和实际内容。证明准备在 Push 前完成、部署使用已准备的同一产物；缺包、错版本、输入变化和验证失败不能继续部署。
5. **XHandoff 内容与冻结。** 验证来源提交关联、完整覆盖、结构化校验、有界引用、运行条件、产物限制与建议 Skill；缺失、矛盾、重复和敏感信息被拒绝或按契约处理。批次冻结后，后续修复不能覆盖原交接。
6. **交接消费。** 验证 XUpdate 采用仍有效的入口与环境经验，对失效信息局部补查，保留原交接；历史通过记录不豁免最终组合检查，产物描述不等于实际产物有效。
7. **工作区与缓存。** 沿用真实 worktree 和工程构建入口测试，验证修复与更新产物独立、依赖缓存可复用、已有封存缓存按输入匹配。明确后端依赖缓存不等于后端完整包缓存，不增加未实现的复用承诺。
8. **通用部署证据。** 从真实命令观察入口验证工作目录、环境、提交、约定版本及验收结果的关联。覆盖退出非零、仅打印成功文字、伪造回执、其他环境结果、旧约定结果和错误版本；不能通过删除旧特殊识别来放宽成功条件。
9. **中断与恢复。** 在准备、Push、部署和回报边界中断，验证使用固定规则包和可信来源恢复，先检查实际状态，再执行剩余步骤；结果未知不当作成功，也不盲目重做副作用。
10. **规则包完整性。** 扩展现有 Bundle 管理测试，覆盖三份 Skill 一起安装和定位、缺失 XHandoff、内容不匹配、安装更新后旧 Task 恢复，以及不可用依赖的明确反馈。
11. **多工程交付。** 在单次执行中覆盖前后端不同约定与环境，验证全部所需检查和 Push 完成后才按既有顺序部署，逐工程证据不串用，部分成功不自动回滚，全部成功后才推进整批 Bug。
12. **真实 Codex 行为。** 扩展现有交接与执行评估入口，在隔离工程、真实 Git 远端和假部署目标上，让 Codex 实际读取文档、使用 XHandoff 并执行 Repair 到 Update。保留采用的文档与 Bundle 身份、真实命令记录、构建和部署结果；规则包静态检查与预写沙盒操作只能作为补充。
13. **切换与历史。** 用合成数据验证旧命令字段退出执行契约、环境身份可匹配、历史事实不被改写、活动任务与固定规则包不被静默替换。破坏性转换使用隔离数据先验收，不借测试操作真实业务数据。
14. **真实工程适配。** 对当前前端与后端文档逐项核对实际入口和行为，覆盖修复的当前工作区构建及更新的正式产物准备。真实 84/85 部署仅在相应环境明确授权后执行；脚本单独实测与平台自动完整链路的证据分别报告。

现有先例包括提测场景装配中的交接冻结与恢复测试、xapt 的真实 worktree 和部署命令证据测试、Skill Bundle 管理测试，以及修复交接的真实 Codex 评估入口。工程自身的构建与部署测试负责证明脚本行为，平台链路负责证明正确选择、顺序、关联与状态推进。

## Out of Scope

- 不重做 PersonAgent、AgentParty 的协作模式、提测成员关系、Bug 生命周期或更新调度。
- 不建设新的 CI/CD 产品、通用流水线引擎、远端构建服务或 xapt 通用产物仓库。
- 不把工程文档变成平台上的另一套命令表单，不要求平台复制和维护各工程全文。
- 不搬运整个修复会话、聊天日志或可写构建目录，不承诺后端自动复用修复阶段的 JAR。
- 不以 XHandoff 建立跨 Bug 的长期经验库，不允许建议 Skill 扩大任务授权或绕过固定 Bundle。
- 不改变已有评审要求，不以打包或启动标记替代工程要求的测试与业务验收。
- 不默认让修复会话 Push 或部署，不自动回滚部分成功，不执行目标工程的数据库 SQL 或数据修正。
- 不在本次规格交付中生成或安装 SSH 密钥、操作真实 84/85 环境、迁移真实数据库、升级本机 xapt 或切换活动会话。
- 工单使用本地文件。GitHub Issue、PR、Release 和现有运行环境切换另有授权边界。

## Further Notes

本规格汇总当前对话已经确认的设计；测试主边界已由用户确认。`ready-for-agent` 表示可以据此实施，不表示功能已经完成、真实自动链路已经验证，或实际环境切换已经获得授权。

规格制定时，平台保存部署命令，XUpdate 按工程文档发现准备命令，后端部署入口单独消费构建产物。此前真实 84 部署在主对话中直接从后端原仓库执行，证明了当时脚本链路可用，不等于平台自动 Update 已完成本文要求的真实工程端到端验收。

当前后端正式构建使用 Colima 虚拟机内的 Docker、Maven 和 Java 8，保存 Maven 依赖缓存，并将与提交匹配的 JAR 返回当前工作区。依赖缓存与项目完整产物缓存不同。工程适配必须特别验证修复工作区未提交内容、不同 worktree 的容器可访问性，以及正式准备入口的干净提交要求，避免用发布入口替代修复验证而漏掉修改。

本规格细化并调整既有统一脚本交付方案中“平台保存具体部署命令”的决定，将命令归属移至工程约定；仍保留本机脚本执行、普通 Push、真实部署验收和业务冻结原则。实施时同步修正相关 ADR 中的配置归属及过时的实现状态说明，不改写历史执行事实。

## 实施约定

两个示例工程均通过 `.xapt/README.md` 定义执行约定并引用已有详细文档。后端引用本机部署文档，使用 Java 8 / Maven 容器。修复打包流式复制当前 worktree，正式准备流式复制干净提交。两个阶段共享 Maven 依赖卷，产物各自保存在对应工作区。前端引用测试构建文档，按 Node 20 和既有 pnpm 锁文件运行。正式准备记录工作区提交、构建输入和静态文件清单，部署校验并上传同一份静态文件，恢复按留存清单只读核验远端。

工程将 `.xapt/README.md` 纳入版本管理。该文件包含且仅包含一个 `xapt-delivery` 围栏块，JSON 对象含 `prepare` 和 `environments`；部署配置直接放在该文件，不通过其他文档间接发现。每个环境项含唯一的 `key`、`deploy`、`verify`。命令从工程根目录独立执行，复杂 shell 编排放在仓库脚本里。部署和恢复入口在验证通过时输出一条带 `commit`、`artifactSha256` 和 `environmentKey` 的 `XAPT_DEPLOYMENT_V1` 回执，并成功退出。xapt 从提交读取固定路径，将同一工作区的真实命令回执绑定环境、约定摘要和执行命令摘要。固定文件缺失或配置无效时明确失败，不要求补充 AGENTS.md 链接。

平台 Schema 35 仅保存环境身份和冻结交付范围。部署命令的旧配置保留在离线迁移的备份，已完成的历史结果和原始执行记录保留。预检拒绝尚未结束的执行、交互和更新批次，环境标识按显式映射转换。
