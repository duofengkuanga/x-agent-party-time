# PersonAgent 多工程提测与统一脚本交付

## Problem Statement

测试负责人登记问题时，需要先判断它属于前端、后端还是两端。实际问题往往来自接口配合或跨工程行为，测试人员未必掌握技术归属；先分诊、拆 Bug、转交工程和关联验收增加了操作负担，也打断了完整问题的上下文。

高频场景是一名开发负责人通过一个 Agent 同时维护前后端。现有按工程分别绑定、修复和交付的流程仍适合多人协作，但缺少单个会话跨工程处理一条 Bug 的能力。执行协议、工作区、结果校验和更新批次也仍以单工程为基础，不能只隐藏表单中的工程选择就解决问题。

各工程现在都计划使用本地部署脚本，继续维护 CI/CD 部署模式及人工回报外部流水线结果没有实际需要。多个 worktree 若重复准备依赖或重复打包，会增加时间和磁盘开销；若直接共享可变构建产物，又可能交付错误版本。历史数据、原会话、失败提交和部分部署成功的状态也必须保留真实含义。

## Solution

创建 Test Submission 时选择 PersonAgent 或 AgentParty，默认 PersonAgent，并明确提示创建后不能切换。PersonAgent 由一名开发负责人、一个 Agent 覆盖参与工程，另一名测试负责人验收；AgentParty 保留原有按工程分工、独立修复和关联 Bug 的流程，不强制工程负责人或 Agent 必须互不相同。既有提测归为 AgentParty。

PersonAgent 的测试负责人只描述问题，仍可选择“仅登记”或“登记并修复”。一条 Bug 始终是一条业务记录，Codex 在同一个持续会话中调查所有参与工程，按证据决定改动范围，不要求测试选择前后端。自动修复串行，修复与更新可并行。工程可追加，不提供移除；新范围从下一轮自动修复开始生效。

已完成的修复按同一张 PersonAgent 提测单汇入一个跨工程 Update Batch，保留最后产生新候选后等待五分钟自动更新及“立即更新”。所有工程统一配置本地部署脚本。整批完成集成、验证和普通 Push 后，按固定顺序部署实际有改动的工程，默认后端先、前端后；全部成功后，该批 Bug 统一进入待验证，随后逐条验收和返修。

各工程保持独立 worktree，依赖优先通过软链接复用，构建产物在各自工作区生成。工程已有的封存缓存按最终构建输入匹配，能复用时省去重复编译；缓存定时淘汰，活动读写受到保护。人工等待沿用现有设计，不在本次引入新的 hook 或问答续接机制。

## User Stories

1. 作为提测创建人，我希望新建提测默认选中 PersonAgent，以便快速进入常用的单人开发流程。
2. 作为提测创建人，我希望仍能选择 AgentParty，以便继续使用按工程分工的多人协作方式。
3. 作为提测参与者，我希望创建前能明确看到所选模式及不可切换提示，以便理解这张提测单后续的处理方式。
4. 作为已有提测的参与者，我希望历史提测保留为 AgentParty，以便原有工程分工、关联 Bug 和历史记录继续有明确含义。
5. 作为 PersonAgent 开发负责人，我希望一次选择自己和一个 Agent 来处理全部参与工程，以便不用给每条 Bug 重复分配执行节点。
6. 作为测试负责人，我希望测试职责仍由另一人承担，以便保留独立验收。
7. 作为提测创建人，我希望使用平台现有的 Engineering、Binding、目标分支和环境配置，以便不用另外维护对应的 Codex 桌面项目。
8. 作为开发负责人，我希望系统检查所有参与工程都绑定到同一负责人和 Agent，以便修复会话能访问完整的工程范围。
9. 作为提测参与者，我希望活动提测可以追加工程，以便后续发现新的相关工程时继续处理原问题。
10. 作为提测参与者，我希望本次只追加、不移除工程，以便保留清晰的工程和交付关系。
11. 作为测试负责人，我希望尚未开始的排队 Bug 在启动时使用最新工程范围，以便追加工程后无需重新登记。
12. 作为开发负责人，我希望运行中的一轮保持原范围，以便任务不会执行到一半突然更换上下文。
13. 作为测试负责人，我希望旧 Bug 返修仍使用原会话并纳入新增工程，以便保留已有调查上下文。
14. 作为开发负责人，我希望工程第一次进入自动修复范围前可以更正目标分支、之后锁定选择，以便避免已开始的修复被投向另一个分支。
15. 作为测试负责人，我希望缺陷内容只填写缺陷描述和附件，以便用一段文字说明问题及复现过程。
16. 作为测试负责人，我希望保留“仅登记”和“登记并修复”两个入口，以便自行决定何时启动处理。
17. 作为提测参与者，我希望 Agent 离线时请求可以排队，并清楚区分等待、准备和正在执行，以便不把登记成功误认为已经开始修复。
18. 作为开发负责人，我希望 Codex 能在同一条 Bug 中修复前端、后端或两端，以便完整处理实际问题。
19. 作为开发负责人，我希望已确定范围内的调查、修改、验证和本地提交连续完成，以便不增加一次诊断完成后的审批。
20. 作为开发负责人，我希望资料不足、预期有歧义或需要范围外工程时暂停澄清，以便关键决定不被模型猜测。
21. 作为提测参与者，我希望同张 PersonAgent 提测单的自动修复逐条执行，以便多个修复不会同时争用同一组工程资源。
22. 作为开发负责人，我希望更新已完成的修复时仍能继续处理后面的 Bug，以便部署等待不阻塞全部工作。
23. 作为开发负责人，我希望已有同步审批和问答仍可通过平台处理，以便继续使用熟悉的交互方式。
24. 作为开发负责人，我希望异步问题仍能在原 Codex 会话中处理并同步结果，以便本次不被迫切换人工接管方式。
25. 作为提测参与者，我希望知道自动串行不限制平台外手动续接，以便理解人工处理与其他自动修复仍可能重叠。
26. 作为开发负责人，我希望所有参与工程准备成功后才开始会话，以便缺少一个工程时不会给出不完整的诊断结论。
27. 作为开发负责人，我希望修复失败后保留未提交内容和已创建提交，以便重试能够继续完成已有工作。
28. 作为开发负责人，我希望成功重试覆盖累计未交付改动，以便前一失败轮已经创建的提交不会漏入交付。
29. 作为测试负责人，我希望只有整条 Bug 修复完成后才进入更新，以便前端修好、后端失败时不会被当作问题已解决。
30. 作为测试负责人，我希望经验证确认目标已经修复的 Bug 能进入待验证，以便不制造没有必要的提交或部署。
31. 作为开发负责人，我希望同张 PersonAgent 提测单已修好的 Bug 统一成一个更新批次，以便前后端一起安排交付。
32. 作为开发负责人，我希望保留五分钟自动更新和“立即更新”，以便兼顾批量合并与及时交付。
33. 作为开发负责人，我希望批次冻结后保持成员和顺序不变，以便运行中的更新不会混入后来完成的修复。
34. 作为工程配置维护者，我希望所有模式都只填写部署脚本，以便不再维护 CI/CD 部署分支和人工外部结果入口。
35. 作为开发负责人，我希望部署使用明确的真实命令，以便缺少脚本时报告缺项，而不是执行占位命令。
36. 作为开发负责人，我希望整批集成、验证和评审完成后才 Push，并在全部所需 Push 确认后才开始部署，以便交付对应最终组合。
37. 作为开发负责人，我希望默认先部署后端再部署前端，只部署实际有改动的工程，以便执行顺序明确且没有多余部署。
38. 作为测试负责人，我希望整个批次全部部署成功后才统一进入待验证，以便验收面对完整的一批更新。
39. 作为开发负责人，我希望部分部署成功时保留已成功版本，不自动回滚，以便按真实现场处理失败的一端。
40. 作为开发负责人，我希望中断或回报丢失后先核实实际状态，再继续未完成步骤，以便不重复 Push 或部署已经成功的内容。
41. 作为测试负责人，我希望任一参与工程失去环境占用时整张 PersonAgent 提测暂停更新和验收，以便不会测试混合的环境版本。
42. 作为开发负责人，我希望环境失去占用时仍能修复，并在重新取得环境、确认版本后恢复交付，以便保留工作进度。
43. 作为测试负责人，我希望批次更新后逐条验收 Bug，并在失败时回到原会话，以便问题与处理历史始终连续。
44. 作为开发负责人，我希望已交付后返修使用当前目标分支的新工作区，同时保留原会话，以便不会长期在过时代码上修复。
45. 作为开发负责人，我希望修复和更新使用各自的 worktree，且每个仓库独立核对身份与提交，以便不影响原始检出目录，也不串用前后端结果。
46. 作为开发负责人，我希望相容的依赖通过软链接复用，以便降低多 worktree 的初始化时间和磁盘占用。
47. 作为开发负责人，我希望确需修改依赖时只给相关工作区准备独立依赖，以便不通过共享链接改坏主仓库或其他任务。
48. 作为开发负责人，我希望构建产物与工程生成目录在 worktree 准备时不软链、不搬运，以便当前构建使用自己的产物。
49. 作为开发负责人，我希望 Node 命令按当前工程、当前 worktree 的 `.nvmrc` 选择并核对版本，以便不同工程不会被套用统一运行时。
50. 作为开发负责人，我希望修复阶段封存的产物在更新阶段输入匹配时可复用，以便省去重复编译。
51. 作为开发负责人，我希望内容相同但提交 SHA 不同的 worktree 也能匹配产物，以便 cherry-pick 不会无谓地使缓存失效。
52. 作为测试负责人，我希望多 Bug 合并改变最终输入时重新构建，以便不会部署某条 Bug 单独打出的包。
53. 作为开发负责人，我希望缓存缺失、损坏或输入变化时明确重建或失败，以便不误用不完整产物。
54. 作为开发负责人，我希望只改变工具缓存存放位置不会破坏产物复用，而真正影响产物的参数变化仍使缓存失效，以便隔离与性能能够同时成立。
55. 作为开发负责人，我希望封存缓存每天检查，七天未使用时可清理，单仓库超过 5 GiB 时优先淘汰最久未使用的内容，以便磁盘占用不会持续增长。
56. 作为开发负责人，我希望缓存读取、封存和清理互斥，活跃产物受到保护，以便定时清理不会破坏正在进行的任务。
57. 作为开发负责人，我希望清理范围仅限登记的派生缓存，过期后可重新构建，以便源码、提交和工作区不会被缓存维护误删。
58. 作为开发负责人，我希望 Cleanup 检查会话、候选、草稿和未提交内容的引用，以便干净的 Git 状态不会被误认为所有内容都可删除。
59. 作为提测参与者，我希望部分清理失败仍有准确记录并可重试，以便业务完成不掩盖资源尚未释放的事实。
60. 作为测试负责人，我希望看到业务状态和验证摘要，以便根据实际结果验收问题。
61. 作为开发负责人，我希望看到必要的技术详情，以便定位失败并作出处理决定。
62. 作为 Agent 使用者，我希望本机绝对工程路径和认证信息留在本机，以便平台业务处理不暴露本机私有信息。
63. 作为开发负责人，我希望重复请求、结果重放和状态同步幂等，以便一次执行不会被重复交付或重复推进状态。
64. 作为历史提测参与者，我希望旧 Bug、批次、人工确认和清理失败记录保留真实含义，以便移除 CI/CD 不会把历史伪造成脚本部署成功。
65. 作为开发负责人，我希望旧会话和原 Skill Bundle 的续接经过真实验证，以便升级失败时得到明确阻塞，而不是被静默换会话或换规则。
66. 作为维护者，我希望先在隔离环境完成实现和验证，再执行有备份、可核验的数据切换，以便真实数据和部署不会成为设计试验材料。
67. 作为开发负责人，我希望性能收益来自实际缓存命中和真实耗时测量，以便不把模拟测试的通过误认为更新时间已经缩短。

## Implementation Decisions

1. **协作模式属于 Test Submission。** 创建输入明确包含模式，默认选择体现在创建界面；模式保存后不可修改。PersonAgent 固定统一开发负责人和 Agent，测试负责人另设；AgentParty 保留原有工程级分工及关联 Bug 行为。
2. **工作范围与改动范围分开。** PersonAgent 的 Bug 归属提测单；每轮 Repair Attempt 保存参与工程快照，结果按工程记录实际提交、人工数据库操作和 Repair Handoff。某工程可被用于调查和验证，并不意味着必须修改或部署。
3. **范围在领取时固定。** 提测业务通过运行时装配向通用 Execution 提供本轮输入解析。范围、版本、资源检查、目标分支首次锁定与领取在同一事务中完成。排队任务读取最新范围；已领取的执行、技术恢复和已冻结批次继续原快照。新的业务返修可以读取追加后的范围。
4. **沿用模块职责。** Project 和 Engineering 模块管理成员、绑定与环境；提测模块决定模式、Bug、修复和交付语义；Execution 模块管理租约、交互、调度和结果；xapt 处理本机工作区和证据。Git、验证、提交、Push 与部署由 Codex 按工程规则及 Skill 执行。
5. **通用执行协议使用工作区集合。** 一个 Execution 仍由一个 Agent 执行，包含主工作区引用和成员集合。单工程使用长度为一的集合，不并存旧单目录协议与新集合协议。Server 只保存工程、Binding 和工作区引用；绝对路径在本机解析。
6. **复用逐仓库 worktree 管理。** 修复使用独立分支，更新使用另一组 detached worktree；逻辑分组不要求重写现有物理目录布局。全组准备成功后才启动会话，部分准备失败时保留可信成员记录并幂等恢复。
7. **一个会话明确多个工程。** 主工程在首次修复时确定，追加工程不改变主工程身份。每次继续明确提供本轮目录映射和范围，分别读取各工程规则、执行命令和校验结果。检测同仓库、同交付目标的重复或冲突配置，不能把不同 Binding 标识当作已经隔离。
8. **区分重试与交付后返修。** 普通失败、技术恢复和人工接管保留原工作区；交付完成后的新返修从当前目标分支准备下一组工作区，继续原 Session。旧组有额外未登记改动时停止自动轮换，不丢弃内容或改写旧分支历史。
9. **持久化未交付代码事实。** 每个工程保留固定的原始基线、每轮起点、观察到的提交及其验证来源。失败轮产生的提交先作为草稿保留，不能被下一轮当前 HEAD 覆盖；成功 Repair 验证完整累计范围后，才把它们登记为候选。历史失败仍保留失败结果。
10. **逐仓库验证结果。** 所有参与工程都检查实际工作区状态与提交范围，不仅检查模型声称有改动的工程。未知工程、跨仓库 SHA、缺失基线、身份不符或无法解释的历史变更阻止候选晋级；不猜测或静默过滤。
11. **共享依赖、隔离产物。** 相容的依赖优先软链复用，已有私有内容不被覆盖。需要安装、清空或升级依赖时先解除当前工作区的链接，再独立准备；不能回写共享目标。构建产物、工程生成目录和需要独立的可写缓存按实际配置排除或定位。
12. **运行时按工程解析。** 每个工程和本轮工作区使用自己的运行时声明，执行前核对实际版本；切换工程重新解析。缓存匹配包含实际运行时，不能把某次测试使用的版本推广为全局要求。
13. **产物复用由工程构建入口负责。** 沿用已有按构建输入封存并校验产物的机制，不新建 xapt 通用产物仓库。Update 在最终组合上重新匹配；命中时恢复校验过的产物，未命中时构建一次。源码、依赖声明、运行时和语义构建参数保持在匹配条件中；仅决定缓存位置的参数在核实后归一化或排除。
14. **缓存维护是有界的本机操作。** 工程提供边界明确的维护入口，xapt 后台按已登记入口调度。默认每 24 小时检查、七天未使用可淘汰、每仓库 5 GiB 软上限；新封存后也检查容量。成功使用更新访问记录，旧条目首次纳入管理以发现时间起算。
15. **缓存清理不与使用竞争。** 读取、恢复、封存、发布和清理共用跨进程互斥；清理拿不到锁则跳过。删除前再次检查候选，先移出可复用集合再删除，不跟随软链接越界。活跃条目可暂时超过软上限；清理失败记录后重试，缓存缺失只导致未来重新构建。
16. **自动修复串行、更新独立。** 同张 PersonAgent 提测单的自动 Repair 共用串行约束，Update 使用独立约束。Agent 容量按会话计数，不按仓库数量重复计算。仓库目标分支、环境和工作区冲突按集合一次性核对，避免只占一部分资源。
17. **人工等待保持原有设计。** 同步审批和问答继续使用 Interaction；异步问题继续交给原会话处理并由负责人同步。保护原会话、工作区和清理引用，不新增人工等待期间的提测级独占，也不承诺限制平台外手动并发。
18. **PersonAgent 的环境条件整体判断。** 任一参与工程失去占用时暂停整张提测的更新与验收，修复继续。重新取得环境并确认版本后恢复；更新领取、环境转交和验收必须在服务端检查，不能只禁用按钮。AgentParty 保留按工程处理的规则。
19. **更新批次统一冻结。** PersonAgent 按提测单收集已完成修复的待交付候选，末次新候选重置五分钟窗口，也允许立即冻结；AgentParty 按提测项分组。成员、顺序、工程映射、目标和部署配置冻结后不因新 Bug 或新增工程而改写。
20. **逐工程执行、整批完成。** 所有参与工程完成集成、验证及适用评审后才 Push，全部所需 Push 已确认才开始部署。后端先于前端，同类工程顺序明确保存在批次中，仅部署实际变更工程。全部所需部署成功后在同一事务推进该批 Bug，随后逐条验收。
21. **保留可核验的阶段事实。** 每个工程分别记录集成代码、验证覆盖、远端确认和部署证据及其来源；代码或输入改变使相应旧证据失效。回报丢失时先核实实际状态，结果未知不能当成功跳过，也不能当失败重做。部分成功不自动回滚，重试继续原批次。
22. **部署契约统一为真实脚本。** 工程配置删除部署方式判别与备用脚本字段，所有模式只保留非空真实命令。移除仅 Push 的更新业务终态、等待外部部署、人工外部报告及其专用表、附件关系、交互和投影；普通 Git Push 和校验继续保留，通用人工交互不受此项删除影响。
23. **规则包和结果契约协调切换。** 新任务使用新版规则；旧 Session 保留原 Task Skill Binding。每轮输出 Schema 与本轮范围及断言匹配，旧会话真实续接不通过时阻止切换，不静默换包、换会话或恢复旧协议分支。
24. **历史展示与未来执行分开。** 离线转换保留旧提测、Bug、批次、人工确认、失败与清理记录的事实和关联。旧“已推送”与人工确认成功分别保留，不能伪造成脚本执行；旧审计资料不能触发旧部署流程。迁移使用最新 Schema，不增加双写、兼容 adapter 或占位默认值。
25. **清理按归属和引用执行。** 工作区 Cleanup 沿用业务结束后的入口，覆盖各工程和历次工作区；同时检查未提交内容、未交付草稿、候选与有效引用。逐成员记录结果，失败可恢复，不能因部分成功就把整组标为已清理。
26. **性能与正确性分别验收。** 复用产物只省掉可以证明重复的构建，不豁免必需的测试、评审和部署验收。记录真实缓存命中、构建次数、更新历时和磁盘占用，不预先承诺固定提速比例。

## Testing Decisions

以**现有生产和场景测试共用的提测工作流装配**为主测试边界，配合现有 Agent 公开协议适配器，从参与者操作、任务领取到结果回报观察业务行为。尽量在这一入口覆盖完整流程，不为每个新增内部函数建立一套平行测试。

测试断言面向可观察结果：模式及权限校验、工作区投影、队列行为、实际 Git 提交、产物字节、部署回执、幂等状态推进和历史保留。内部表名、调用次数或私有辅助函数的形状不作为需求正确性的替代证据。

1. **创建和配置。** 覆盖默认 PersonAgent、显式 AgentParty、不可切换模式、统一负责人和 Agent、独立测试负责人、追加工程但不能移除，以及目标分支首次进入范围后的锁定。
2. **范围与竞争。** 从公开业务入口触发追加、排队、领取、环境转交，核对排队任务使用最新范围、运行中快照不变、冻结批次不变，以及版本和资源竞争时不会领取半份范围。
3. **Bug 与调度。** 覆盖两个登记入口、离线排队、单端和双端修复、同提测自动串行、修复与更新并行，以及 AgentParty 的原有关联 Bug、转交、协作和验收回归。
4. **人工交互。** 保留同步审批／问答与外部会话交接的现有协议测试；核对新集合协议中的原会话、全部工作区和同步来源均受到正确保护，不新增隐式回答或恢复。
5. **真实 Git 技术边界。** 复用现有临时 Git 仓库和真实 worktree 测试方式，验证两仓库身份、不同分支、detached 更新、部分准备失败、重复恢复及清理。只用预写 SHA 不能证明跨仓库结果正确。
6. **失败提交恢复。** 必须覆盖第一轮创建提交后失败、第二轮继续提交、全部累计改动只交付一次；还要覆盖没有新增提交、仅验证旧草稿的成功重试，以及回报前进程退出、异常历史和交付后轮换。
7. **跨工程交付。** 延续现有批次冻结、五分钟窗口和并发测试，扩展到多工程。验证全部验证后才 Push、全部 Push 确认后才部署、后端失败停止前端、整批成功才待验证，以及同仓库目标或环境不能被冲突批次占用。
8. **副作用后的中断。** 在每个 Push、部署和结果回传边界注入中断，检查已经成功的事实不会被丢弃、重复回报幂等、不盲目重复部署、不自动回滚；环境或代码变化必须使相关证据重新核实。
9. **工程产物缓存。** 沿用现有工程构建入口的真实 Git/worktree 测试，覆盖提交前构建、不同 SHA 的 cherry-pick、额外 Bug 合入、配置与运行时变化、损坏缓存、软链保护及独立输出。区分模拟编译测试与真实编译验收。
10. **共享依赖与缓存路径。** 验证普通任务复用依赖、修改依赖时只影响自己的工作区；独立可写缓存不会造成产物互相覆盖。只改缓存存放位置应仍命中，改变语义构建参数应失效。
11. **周期淘汰。** 使用可控制的时间和隔离缓存目录验证 24 小时周期、七天过期、5 GiB 软限额、活跃内容保护、进程中断、锁恢复、删除部分失败、目录软链和越界路径。观察保留和删除的实际文件，不依赖真实等待天数或真实大体积测试数据。
12. **迁移与历史。** 用合成旧数据覆盖本次实际发现的旧部署配置、历史推送与人工确认、幂等回执、已处理交接和清理失败。验证记录及关联的保留、错误阻止应用、备份可核验，缺少真实脚本时不得用默认命令补齐。
13. **真实 Codex 行为。** 在隔离工程、假远端和假部署目标中验证同会话多目录、按工程结果、范围追加、真实恢复及旧 Skill Bundle 续接。现有协议替身和规则包 Hash 校验不能代替这一层；实际旧版本组合均需覆盖或明确报告未覆盖原因。
14. **页面与角色。** 在既有浏览器测试入口验证模式选择、双登记入口、队列和失败反馈、整批待验证、配置锁定及环境暂停。遵守项目现有视觉规范和用户指定的 Dia 连接；技术信息的权限过滤在响应层也要验证。
15. **性能。** 分别测量输入命中、输入变化和多 Bug 集成的真实构建次数与历时，以及依赖复用和缓存清理后的磁盘占用。只有实测结果才能支持提速结论。

既有先例包括：协议级 Agent 的失败修复与会话同步场景、生产共用装配中的更新并发和批次冻结场景、真实 Git worktree 隔离测试，以及工程构建缓存与部署入口测试。优先扩展这些入口。通用工作区、结果校验和工程缓存是无法由业务模拟替代的必要技术边界；不因此扩大为全新测试框架。

## Out of Scope

- 不移除 AgentParty，不要求其参与者或 Agent 必须互不相同。
- 不允许活动提测切换模式，不提供移除参与工程。
- 不把 PersonAgent 扩展为跨电脑、多 Agent 的协调执行，也不新增已有任务换机或重新绑定能力。
- 不改造人工等待，不加入 Ikaga／hook 接入、异步问题网页自动续接或平台外会话的强制串行控制。
- 不合并前后端 Git 仓库，不把同一会话解释为只有一个 worktree。
- 不强制每个 Bug 做全部发布检查，不跨不同构建输入复用包，不以缓存命中替代必要验证。
- 不自动回滚部分部署成功，不代替目标工程执行数据库 SQL 或业务数据修正；已有人工数据库交接继续保留工程归属。平台自身的离线 Schema 转换按迁移验收和实际操作授权处理。
- 不删除本仓库自身的代码质量 CI。移除范围是产品内工程交付所用的 CI/CD 部署模式。
- 不以此次 spec 交付启动代码实现、真实数据迁移、清理已有资源或执行部署。
- 不创建 GitHub Issue、PR 或 Release，不重建外部工单关系。

## Further Notes

本 spec 汇总当前已确认范围，不重新访谈。`ready-for-agent` 表示可以据此组织实施任务，不能解读为功能已实现、真实模型已验证或实际切换已获授权。测试边界沿用会话中已经讨论的生产共用装配、公开 Agent 协议和必要的真实执行边界。

后端真实部署脚本尚未准备好。代码实现、合成迁移测试和隔离验证可以推进；真实切换和后端部署必须等准确命令与验收方式确定，不填占位命令。

已有只读历史盘点显示，当次检查没有在途修复或更新，历史 Bug 和批次已完成；仍有活动提测、旧 CI/CD 配置及失败清理记录。实际切换前必须重新核对当时数据，保持原有事实和状态，不把旧报告或已处理交接误作新任务。

已有证据仅覆盖部分基础：工程缓存与部署入口的 17 项隔离测试通过；8 组历史 Skill 绑定可解析；临时 Git 诊断已复现普通重试基线遗漏前轮范围的边界，以及独立工具缓存路径导致现有产物缓存失配的问题。这些证据不等于新方案的端到端验收通过。
