# PersonAgent 恢复、证据与旧会话设计

本文补充 [主技术设计](personAgentExecutionDesign.md) 的故障路径。产品规则以 [ADR-0016](../adr/adr0016ChooseAnImmutableSubmissionMode.md) 和 [ADR-0017](../adr/adr0017UseDeploymentScriptsForEveryEngineering.md) 为准。下述状态和数据结构是待实现的技术提案，不是当前能力或已经通过的测试。

## 环境与目标分支

PersonAgent 的更新与验收检查整张提测单的参与工程环境：全部仍由本提测占用且版本已确认，才允许开始交付或接受测试验收；只修改前端也不能绕过丢失后端环境的情况。自动修复不因此停止。

范围解析、目标分支锁定、工程配置版本检查、资源检查和 Execution 领取在同一事务边界中完成。该次领取成功是本轮开始准备执行的时点；没有领取的排队任务仍可使用最新工程范围。各工程首次纳入快照时写入锁定事实；后续准备或执行失败不会静默解除已经使用过的分支配置锁。

PersonAgent 有正在更新的批次时，沿用“更新中环境不可转交”的保护并覆盖本提测的参与工程，避免部署中途被平台内另一张提测接管环境。环境变化与更新领取之间的竞争必须在事务中检查，不能只依靠按钮禁用。已冻结批次的候选与部署对象不因追加工程而扩充；若当前环境条件不满足则等待，不改写批次。

已经启动的外部命令不因界面刷新而被盲目中断。平台外对环境的改动无法由数据库锁阻止；继续执行或重试前发现版本矛盾时进入待核实或现有人工处理路径。

## 失败提交与可交付候选分开

### 数据关系

为每个 Bug、工程及一次尚未完成交付的工作区记录以下事实：

| 事实                             | 含义                                                                     |
| -------------------------------- | ------------------------------------------------------------------------ |
| 固定的原始 Git 基线              | 该工作区准备完成、首次执行前的 HEAD；普通重试不能覆盖它                  |
| 每次 Execution 的开始和观察 HEAD | 用于区分本轮新变化与前轮已经留下的变化                                   |
| 按顺序观察到的提交               | 完整 SHA、工程／工作区归属、首次观察来源；不把观察时间伪造成准确创建时间 |
| 提交的交付资格                   | 草稿、已通过验证的候选、已交付，或有依据地作废；失败不等于删除           |
| 验证来源                         | 哪一次成功 Repair 对完整候选集合做了验证、评审并提供 Handoff             |

“草稿”仅是内部未交付代码事实，不增加测试人员需要维护的 Bug 状态。通用 xapt 负责记录和核对工作区事实；提测模块决定何时具备交付资格。

### 执行与恢复

1. 开始前保存原始基线和本 Execution 起点，确认工作区身份、已知提交和未提交改动。
2. 正常完成、失败或恢复时，读取各仓库的实际提交范围和工作区状态。已提交但尚未获得成功 Repair 认证的改动保持草稿，未提交文件也留在原工作区。
3. 若进程在回报前中断，下一次继续先对照持久化的原始基线核对现场。不能以当前 HEAD 建立全新的唯一基线，从而遗忘前轮提交。
4. 整条 Bug 修复完成后，校验累计未交付范围，并对全部工程的相关改动完成验证与评审。成功 Attempt 为该完整候选集合提供 Handoff；以前的失败 Attempt 仍然保留失败结果。
5. 一端已修好而另一端失败时，不发布前者。只有整条 Bug 达到成功条件，相关草稿才成为可冻结进 Update 的候选。
6. Git 状态无法读取、基线不可达、分支身份不符或存在未经解释的历史变更时，不通过猜测筛选提交；停止候选晋级，保留现场并给出明确错误。

例如第一轮从 H0 创建 A 后失败，第二轮创建 B：后续成功验证的候选是同仓库的 `[A, B]`，而不是仅从第二轮起点 A 算出的 `[B]`。A 的首次观察与最终通过验证分别记账，不改写第一轮失败记录。

2026-11-03 使用 `bun --eval` 和自动清理的临时 Git 仓库调用当前 `GitExecutionResultVerifier` 做了最小核验：重试基线确为 A，累计 `[A, B]` 校验失败，仅 `[B]` 校验成功。没有修改仓库源码或数据库，也没有调用模型。此结果证明现有校验边界，尚不构成新草稿恢复方案或完整 Repair → Update 的验证通过。

如果后来确认目标分支已经满足 Bug 的验收要求，必须核实目标状态，并明确处理已有草稿的交付资格。不能用“本轮没有新增提交”推导“没有任何待交付改动”，也不自动删除工作区中的内容。

### 交付后的再次返修

Session 保持同一个，但不要求永久复用同一条 Git 分支。上一批已完成交付后，新的业务返修使用当前目标分支准备下一组工作区；原工作区和提交引用保留到可清理时。向原会话提供本轮的新目录和基线，不重写旧分支历史。

轮换前必须确认旧工作区没有交付后新增、尚未登记的改动；有矛盾时保留现场并停止自动轮换。普通失败重试和技术恢复继续原工作区，不能借轮换隐藏草稿。这样区分“继续同一条业务会话”与“从同一份过时代码重复返修”。

## 跨工程更新的阶段和证据

批次冻结时固定成员、候选顺序、工程映射、目标分支和部署命令。每个参与工程独立记录当前集成 HEAD、验证覆盖、远端确认和部署验收事实，并关联来源 Attempt；记录不能只剩一条整批成功／失败摘要。

| 阶段       | 完成条件                                             | 失败或不确定时                                     |
| ---------- | ---------------------------------------------------- | -------------------------------------------------- |
| 准备与集成 | 各工程包含本批完整候选，Git 操作结束，身份与基线正确 | 不进入验证后阶段；保留固定成员和各工程现场         |
| 验证与评审 | 本批最终组合的必需检查和评审通过                     | 不 Push，不部署；修正后只保留仍有效的既有证据      |
| Push       | 各工程普通 Push 且远端已确认包含应交付的提交         | 已推送的一端保留，全部 Push 未确认前不开始任何部署 |
| 部署       | 有改动工程按固定顺序执行本地脚本并满足工程验收       | 后端失败不继续前端；保留成功部分，不自动回滚       |
| 业务完成   | 全部所需工程的交付事实均确认                         | 同一事务推进整批 Bug；重复回报不重复推进           |

阶段事实必须绑定本批候选、集成代码和部署配置。代码或输入发生改变时，对受影响的证据重新验证，不能仅凭过去的状态位跳过。Codex 文字报告、原生命令结果和工程验收证据要区分来源；记录过“已完成”不能替代恢复时的现场核对。

原生执行结果和终态 Outcome 能取得时通过本机持久化与 Outbox 幂等回传。进程可能在副作用成功、证据尚未保存之间中断，这个窗口不能被假设不存在：此时状态是“待核实”，而非自动成功或自动重做。

### 典型恢复路径

| 中断点                          | 恢复行为                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------- |
| 后端 Push 成功，前端 Push 失败  | 先查远端确认后端实际状态，继续处理前端；尚未开始部署                         |
| 后端部署成功，前端部署失败      | 核实后端仍是本批预期版本，再继续前端；不默认重跑后端                         |
| 部署脚本已运行，但结果丢失      | 读取脚本／工程提供的版本或验收证据；无法证实时沿用现有人工交接，不盲目再部署 |
| 全部部署成功，Server 未收到结果 | 核实后重发同一结果，Server 幂等处理，不重新执行整批                          |
| 远端或环境被平台外操作改变      | 暂停推进，核实差异并使受影响阶段的旧证据失效                                 |

部署成功判据来自工程真实脚本与验收入口；xapt 不臆造通用健康检查，也不把命令已启动当作部署完成。后端真实脚本尚未准备好，因此其具体验收方式仍是切换前需要补齐的工程事实。

## 旧会话与旧 Skill Bundle

保留 [ADR-0009](../adr/adr0009DistributeExecutionSkillsAsLocalBundles.md) 的既有约束：旧 Session 继续使用原绑定的 Bundle，不静默替换规则包，也不新建会话冒充原会话续接。新 Task 使用新版 Skill。

当前实现每次 `turn/start` 都传本轮输出 Schema，且旧 Skill 明确服从调用方 Schema，因此“旧会话＋原 Bundle＋新单工程集合契约”存在验证路径。新范围输入、Git 断言、结果解释必须同时匹配；仅改 Schema 或更换当前 Skill 软链接不足以证明行为兼容。

2026-11-03 对实际历史绑定作了只读核验：8 组不同的 Skill 名称／Bundle Hash／来源版本组合均可由当前 `SkillBundleManager.resolveBound` 解析并通过完整性校验。没有下载或更新 Bundle，也没有运行模型。这只证明旧规则包可用，不证明它们已经能正确使用新契约。

针对实际存在的各版旧 Repair Bundle，需在隔离旧会话中验证：原 Session 不变、单工程范围正确、新结果契约有效、累计提交没有漏报、人工交接和只读同步仍能按对应执行的 Schema 校验。旧 Update 批次全部完成，不重新运行其旧 CI/CD 规则；旧 Cleanup 失败记录保留，不顺便重试。

若旧 Repair Bundle 与新契约的真实验证不通过，阻止实际切换，明确报告具体冲突。此时再讨论是否显式改变 Bundle 固定规则；不能临时加入旧协议 fallback、偷偷换 Bundle 或丢弃历史会话。

## 历史证据与未来执行分开

可执行 Outcome 和历史展示数据分开校验。旧 `PUSHED` 表示当次执行确认了推送；随后人工报告证明部署成功。离线转换保留两个阶段的事实、时间、人员与原始审计依据，生成普通历史展示数据，不能强行把旧执行解析成“本地脚本已完成”的新 Outcome。

新任务只使用最新脚本部署契约。旧输入输出可作为不可执行的审计资料保存，读取历史不再触发 CI/CD 分派或外部报告处理。原始资料、幂等回执和规范化历史展示的转换均需按结构校验；过去没有执行过的命令和验证结果不补造。

旧提测保留 AgentParty。为它们的未来执行准备真实脚本配置时，记录配置生效来源和时间，与过去的 CI/CD 快照分开；不把新配置回填成过去实际使用过的配置。已关闭状态、活动状态和四条清理失败记录均保持真实。

## 必须验证的场景

- H0 → A → FAILED → B → COMPLETED 后，A、B 都进入候选且只交付一次；跨两个仓库也成立。
- 失败后没有新提交，只验证已有草稿，仍能完整登记候选；不能误报目标已修复。
- 回报前进程退出、Outbox 重放和多次失败重试不覆盖原始基线；异常 Git 历史明确阻止晋级。
- 已交付后原 Session 进入新工作区；旧工作区存在额外改动时不自动丢弃。
- 所有工程验证完成后才 Push，所有 Push 确认后才部署；每个中断点都按上表恢复。
- 追加工程、领取修复、分支锁定与环境转交发生竞争时，快照和锁一致；任一环境丢失时整张 PersonAgent 的更新／验收被阻止。
- 各版实际旧 Repair Bundle 的同会话续接、输出与基线校验通过；不能用 Fake Codex 返回预写 JSON 替代此项。
- 迁移前后 Bug、批次、确认事实和关联一致，原 `PUSHED` 从未被描述为脚本执行成功。

以上实现及验证尚未完成。技术方案明确不代表真实执行已通过；其中旧 Bundle 的行为兼容性和真实部署验收必须取得实际证据后才能放行切换。
