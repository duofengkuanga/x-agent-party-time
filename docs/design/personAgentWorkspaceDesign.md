# PersonAgent 工作区设计

方案是“一条 Bug 一组修复 worktree，一个更新批次另一组 worktree，每个 Git 仓库单独创建”。一组工作区由一个 Codex 会话操作；一个会话不要求只有一个仓库。本文补充 [主技术设计](personAgentExecutionDesign.md) 与[恢复设计](personAgentRecoveryDesign.md)，尚未实现。

## 复用现有管理

保留 `GitExecutionWorkspaceManager` 对单仓库的 prepare、resolve、Git 身份检查和私有状态写入。由 `ExecutionPreparation` 根据本轮工作区集合逐个调用，全部准备好后返回主 cwd 和成员目录映射；不为两种提测模式复制 Git 管理器。

分组是逻辑关系。物理目录继续使用现有 xapt `state/workspaces/<工作区 key 的摘要>` 平铺方式；源码仓库、分支／detached 身份与路径映射仍逐工作区保存，不为可读目录层级改写现有路径保护。

本轮 Execution 保存成员和主工作区引用，工作区记录保存各成员的实际状态，不再复制一份容易漂移的独立组注册表。Server 只保存引用，绝对路径由 xapt 本机解析。

逻辑示意如下，名称不代表实际物理路径：

```text
原始前端仓库 ── Bug A 前端修复 worktree ── 前端候选提交 ── 批次 1 前端 worktree
原始后端仓库 ── Bug A 后端修复 worktree ── 后端候选提交 ── 批次 1 后端 worktree
                 同一个 Repair 会话                         同一个 Update 会话
```

原始仓库提供 Git 对象、远端与创建 worktree 的入口，修复和集成在各自 worktree 中进行。Git 对象和引用按原生 worktree 机制共享，用户原始检出目录中的未提交代码不被拿来当作任务源码。

## 创建与身份

- 排队阶段不创建 worktree。领取一轮修复并固定范围后，按所有参与工程创建工作区；任何成员准备失败都不启动 Codex。
- 修复 worktree 使用独立分支，从该工程固定目标分支解析出的准确 Commit 开始，并保存原始基线。沿用现有托管分支规则，补充工程与交付轮次的唯一标识。
- Update 为冻结工程范围准备独立 detached worktree，从目标分支准备基线，再集成相应工程的候选；不复用任何正在修复的目录。
- 工作区身份包括所属仓库、工作区引用、基线、分支／detached 状态和托管路径。重试按身份复用，不能只因为目录存在就使用。
- 多个 Binding 若实际指向相同仓库和同一交付目标，要在准备阶段识别重复或冲突，不能把不同 Binding ID 当作已经隔离；不静默合并语义不明的工程配置。
- 准备过程中断时保留已经创建的成员记录。恢复先逐项核验，再补齐缺失成员；不开始只看见部分工程的修复。

## Codex 如何使用多个目录

首次修复选择参与工程列表中的第一个工程作为主工程，后续追加工程不改变主工程。主 cwd 只是会话起点，不代表 Bug 归属或只能修改该工程。

xapt 为本轮输入提供每个工程的短别名、用途、实际 worktree 路径和允许处理的范围。Codex 分别读取每个工程的适用规则，并在对应目录执行 Git、测试与构建；所有操作不能默认沿用主目录。新增目录的输入在继续原 Session 时显式提供。

每个参与工程的基线、提交和结果独立验证。Update 的冻结范围也包含集成验证需要的工程上下文；本批没有候选的工程不因此自动产生提交或部署。确有必要的集成修正在冻结范围内留证，最终只部署实际发生变更的工程；需要范围外工程时停止并澄清，不能私自扩充批次。

## 生命周期

| 场景                         | 修复 worktree                                            | 会话                                           |
| ---------------------------- | -------------------------------------------------------- | ---------------------------------------------- |
| 首次开始修复                 | 为当时参与工程创建一组                                   | 创建该 Bug 的会话                              |
| 普通失败、程序中断、人工接管 | 核验后继续原组，保留未提交内容和草稿提交                 | 继续原会话                                     |
| 排队期间追加工程             | 开始时按最新范围准备                                     | 按该 Bug 原有会话状态创建或继续                |
| 本轮运行中追加工程           | 本轮不变；下一业务轮次补入新增工程                       | 保持原会话                                     |
| 修复完成、等待更新           | 保留原组作为候选来源，不再自动改写已冻结提交             | 会话保留                                       |
| 更新批次执行                 | 使用另一组 detached worktree                             | 使用批次自己的 Update 会话                     |
| 已交付后测试返修             | 从当前目标分支准备下一组；旧组无额外未登记改动才允许轮换 | 仍是该 Bug 的原会话，新 cwd 和目录映射显式提供 |

“一轮工作区”以一次尚未完成的交付为边界，不是每次 Execution 都新建。否则失败重试会遗失现场；而永远复用旧分支，又会使交付后的返修长期停留在旧代码上。

本轮追加工程只补齐新成员，不重新初始化已有工程。交付后的返修轮换与追加工程是不同操作；二者均需保存本轮准确的工程和目录映射。

## 依赖、配置与构建产物

当前 `mirrorIgnoredRepositoryContents` 会把主仓库现存的全部 Git 忽略项软链到 worktree，实际包括依赖、本机配置及可能存在的构建目录。现有测试也证明通过共享依赖写入可影响其他工作区；因此这不能承担修复与更新并行时的构建隔离。

新方案取消“把全部忽略内容自动软链回来”：

| 内容                                        | 处理原则                                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| Git 跟踪的源码                              | 使用各 worktree 自己的检出                                                         |
| Git 对象库                                  | 原生 worktree 共享                                                                 |
| 包管理器下载缓存                            | 通过工程工具支持的方式复用，不把应用产物当下载缓存                                 |
| node_modules 等依赖目录                     | 每个 worktree 独立准备；安装可利用下载缓存                                         |
| target、dist、build、.next 等构建与运行产物 | 留在对应 worktree，不软链到主仓库或另一 worktree                                   |
| 本机配置和认证                              | 沿用工程明确的本机加载方式，不通过全量复制或软链忽略项隐式带入；缺少配置时明确报告 |

初始化、测试和部署命令继续来自工程真实文档与脚本，由 Codex 执行；xapt 不自动猜测各语言的安装命令。需要本机配置的工程应明确如何为 worktree 提供它，不能把文件系统链接误当成只读权限保护。

该方案会增加独立依赖目录与初始化成本，需要在实际工程验证中测量。并行使用的端口、外部测试数据和服务资源仍由工程明确分配；Git worktree 本身不提供这些资源的隔离。

## 清理

继续以现有业务结束后的 Cleanup 为清理入口，覆盖各 Bug 的各组工作区及批次工作区。不因一次失败、等待人工或阶段完成而马上删除目录。

上游检查会话、候选、更新批次和人工交接的有效引用；本机再次核验归属、Git 状态以及保存的未交付草稿事实。`git status` 干净不代表没有未交付提交，不能单凭这一条件删除修复分支。

按成员仓库逐项清理并记录结果，允许幂等重试。一个成员清理失败时不得把整组记成已清理；继续保留失败记录和需要恢复的引用。正常路径不强制删除脏目录或丢弃尚未交付的提交。

## 验证范围

- 两个真实 Git 仓库、一组 Repair、另一组 Update；一个会话能正确区分工程并返回可验证结果。
- 部分成员创建失败／进程退出后，只补齐缺失成员，旧成员的未提交内容和提交不丢失。
- 失败重试保持原组与基线；已交付返修换组但保持原 Session。
- 追加工程只在下一轮生效，主工程身份保持稳定。
- Repair 与 Update 同时构建时，源码、依赖目录和产物没有通过忽略项软链相互覆盖。
- 已冻结提交、未交付草稿、人工会话或脏目录仍被保护；组清理部分失败可恢复。

截至 2026-11-04，只核对了当前管理器、现有测试定义与调用关系，未实现上述变更，未做多仓库会话或并行构建验证。
