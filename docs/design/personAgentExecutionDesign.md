# PersonAgent 多工程执行技术设计

产品规则已在 [ADR-0016](../adr/adr0016ChooseAnImmutableSubmissionMode.md) 确认；全局移除 CI/CD 的决定见 [ADR-0017](../adr/adr0017UseDeploymentScriptsForEveryEngineering.md)。本文是技术提案，不是已实现能力。本轮只修改文档，尚未执行多工程修复、部署或数据迁移。

## 设计就绪审查

主业务流程及环境、分支规则已确认。此前发现的恢复缺口已有[具体技术方案](personAgentRecoveryDesign.md)，下表区分设计状态与尚未完成的运行验证；产品确认、规则包可解析和文档检查都不等于真实恢复已经通过。

| --------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |

其中“提交后失败”的结论来自源码：`repairProjection.ts` 只在完成结果中累加候选，`ExecutionPreparation.prepare` 会为新 Execution 捕获当前 HEAD，`GitExecutionResultVerifier` 校验新基线到 HEAD 的精确提交范围。已用临时真实 Git 仓库调用现有校验器复现边界：先创建 A，再以 A 捕获重试基线并创建 B，`[A, B]` 被拒绝而 `[B]` 被接受。外部会话同步使用原执行基线，是另一条路径。此核验不覆盖完整 Server 修复到交付流程，也不将结论扩大为所有重试都会丢提交。

## 当前实现与主要变化

| 位置                           | 当前实现                                       | 提议变化                                                                                       |
| ------------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `server/submissions/bugs/`     | Bug 归属单个 Submission Item，跨工程拆关联 Bug | PersonAgent 的 Bug 归属提测单，工程范围与实际改动分别记录；AgentParty 保留单工程归属及关联 Bug |
| `server/submissions/repair/`   | 一个会话、一个工作区、单仓库候选提交           | 一个会话关联多个工程工作区，候选和交接按工程归属                                               |
| `packages/execution-contract/` | 一个 Binding 和一个工作区描述                  | 一个 Agent 上的一组工作区、一个主工作区及通用调度资源                                          |
| `apps/xapt/src/execution/`     | 解析一个目录、建立一个基线并校验单仓库提交     | 按工作区组准备、记录和逐仓库校验，路径继续只留本机                                             |
| `server/submissions/update/`   | 按 Submission Item 计时、冻结和交付            | PersonAgent 按提测单组织一个批次，内部按工程集成、Push 与脚本部署                              |
| 工程配置及更新结果             | LOCAL_SCRIPT / CI_CD 双模式，支持外部部署报告  | 统一部署脚本，完成部署才返回更新成功                                                           |

## 职责与接口

沿用 [ADR-0001](../adr/adr0001KeepRunnerDomainNeutral.md) 的职责划分：提测模块决定协作模式、工程范围、Bug 状态和批次成员；通用 Execution 模块管理领取、租约、会话、交互及结果；xapt 解析本机 Binding、准备工作区和验证证据。Git 集成、测试、提交、Push 与部署继续由 Codex 按 Skill 执行。

两种模式共用执行能力，不复制两套 xapt 或更新实现。模式差异集中在工程范围、Bug 归属、修复排队与批次分组的业务规则中。单工程执行使用长度为一的工作区集合，不保留旧单目录字段与新集合的双轨运行协议。

## 领域数据

1. 提测单保存不可变的模式。PersonAgent 保存统一的开发负责人和 Agent，参与项的 Binding 必须属于该负责人及 Agent；测试负责人仍为另一人。
2. Submission Item 保留工程、目标分支、环境和 Binding。追加工程检查相同负责人、Agent、成员资格及环境占用；不提供移除入口。
3. 将“可供调查的工程范围”和“实际产生改动的工程”分开。某工程出现在修复上下文中，不代表它必须产生提交或部署。
4. 每次 Repair Attempt 保存不可变的工程范围快照；Bug 的持续修复上下文保存一个 Session，以及按工程关联的工作区、未交付提交和 Repair Handoff。
5. 每个候选提交和数据库人工操作都必须有工程归属。不能使用一份混合 SHA 列表或无仓库归属的相对路径；不同 Git 仓库中的提交分别校验。
6. Update Batch 保留一个业务状态和固定 Bug 成员列表，另保存本批涉及的工程、候选、部署命令、顺序及各工程执行事实。批次不能在重试时偷偷增减成员。

以上是需要表达的数据关系，具体表名与字段布局在实现时确定。运行时直接使用新 Schema，不加入 deprecated 字段、双写或兼容 adapter。

## 在开始执行时确定范围

当前 `RepairService.createInitialExecution` 在入队时就生成 Brief 和单工作区描述；若只在这里扩成数组，排队期间追加的工程仍不会生效。

提议在领取一轮尚未开始的自动修复时，由提测模块提供输入解析逻辑，读取最新参与工程并生成固定的工作区集合、Brief、Hash 和结果约束。通用执行模块通过运行时装配调用这一逻辑，不反向导入提测模块。

范围快照、所需资源检查及领取必须在同一事务边界内确定。领取成功后冻结本轮输入，xapt 才做本机准备和启动；运行中追加工程不会改写本轮。

业务返修或新的修复尝试可以读取最新范围。进程重连、租约恢复和 Outbox 重放属于原执行恢复，必须继续原快照，不能借恢复扩大范围。已冻结 Update 始终使用自己的工程和提交快照。

## 工作区组与单一会话

目录布局、创建与复用时机、依赖隔离及清理方案见 [工作区设计](personAgentWorkspaceDesign.md)。

为每条 Bug 的每个参与工程准备独立 Git worktree。选择稳定的主工作区作为 Codex 的 `cwd`；其他工程的本机路径和用途由 xapt 在本机组装后提供给 Codex。追加工程只增加该工程的工作区，继续原 Session，不重建已有工程的修复上下文。

App Server 目前使用一个主 `cwd`。不能假定它会为所有额外目录自动建立 Git worktree，也不能依赖它自动加载副目录的项目规范。工作区准备由 xapt 负责，Skill 明确读取各工程适用的规则，并在对应目录执行 Git 与验证命令。

工作区组必须全部准备成功后才开始 Codex。部分准备失败时保存已经创建的本机记录，后续可幂等复用或清理；不能只把可用工程交给 Codex，再把它误认为完整调查范围。

Server 只保存 Binding、工程与不透明工作区引用，不接收本机绝对路径。供 Codex 区分工程的执行内短别名由本机映射至工作区引用，不暴露平台 UUID；这补充多工程任务所需的最小结构化上下文，仍遵循 [ADR-0011](../adr/adr0011MinimizeCodexExecutionBriefsAndOutcomes.md)。

工作区继续通过软链复用相容的依赖，避免逐份复制和重装；dist、target 等构建产物及工程生成目录在准备阶段排除，不软链也不搬运，由当前 worktree 自行生成。需要变更依赖的工作区才独立安装；共享依赖内的可写缓存、端口和外部测试资源仍需核对，详见工作区设计。该变更尚未实现。

需要 Node 的构建、测试、部署和工程缓存维护命令，均按当前工程、当前 worktree 的 `.nvmrc` 选择并核对实际版本，不设置统一 Node 版本。工程封存缓存另做周期淘汰，保留期限、容量建议及读写互斥规则以工作区设计为准；不在本轮直接执行清理。

## 结果与恢复证据

Server 继续拥有输出 Schema。Repair 结果按工程给出提交、验证与交接，保留一条 Bug 的整体完成结果；没有改动的工程不制造占位提交。

xapt 在开始前为每个工作区记录 Git 基线，结束时逐仓库核对新增提交。所有参与工作区均须检查，避免仅校验模型声称修改的工程而漏掉其他目录中的改动；未知工程别名、跨仓库提交和超出本轮范围的结果都不能接受。

外部会话同步同样读取原执行的范围与各仓库基线。人工等待继续使用已确认的现有交接流程，不增加 hook 或自动问答续接；清理需覆盖该 Bug 或批次拥有的全部工作区，并保留原有会话与后续任务引用保护。

## 调度

PersonAgent 为同一提测单的自动 Repair 提供共同的串行约束；Update 使用独立约束，因此可与下一条 Bug 的 Repair 并行。每次执行仍按一个会话占用 Agent 容量，而不是按仓库数量重复占用槽位。

工作区、仓库目标分支和环境的冲突检查扩展到集合，一次性检查全部资源，不能先占前端再等待后端。两种模式以及不同提测单之间仍遵循现有共享工程、目标分支和环境的冲突保护。

等待人工的原会话与工作区保护按现有规则扩展到整个工作区组，不新增提测级人工独占。自动串行不承诺限制平台外手动操作。

## 跨工程更新

PersonAgent 的待交付计时按提测单聚合；新的候选重置五分钟窗口。冻结只取已经完成修复且有待交付改动的 Bug，运行中的修复留给后续批次。AgentParty 继续按 Submission Item 分组。

先集成本批各工程的全部候选，完成最终组合所需的验证与评审，再普通 Push 并核实远端。更新按各工程已固定的部署命令执行；仅有实际改动的工程参与部署，默认后端在前、前端在后。多个同类工程的执行顺序需要在批次内明确保存，不依赖数据库返回顺序。

每个工程的 Push 与部署事实关联来源 Attempt 和证据。失败时保留已成功部分；恢复时仍核实当前远端、脚本验收结果和未完成步骤，保存的阶段记录不代替现场核验。未知结果不能当作失败重放，也不能当作成功跳过。

只有全部参与工程完成，才在同一业务事务中把该批所有 Bug 推进到待验证。某一工程失败不拆出部分可验收的 Bug，重试仍处理原批次；后续批次等待，其他 Bug 可以继续修复。

## 全局移除 CI/CD

环境只保存一份非空部署命令。新运行时契约移除部署方式判别字段和备用 `scriptCommand`，执行 Brief 直接提供部署命令；不保留只有一个取值的部署模式或隐藏的 CI/CD 分支。

| 范围         | 需要退出或简化的内容                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 工程配置     | 部署方式选择、`CI_CD` 判别分支、切换模式时暂存脚本的字段；统一要求非空的真实部署命令             |
| 更新契约     | CI/CD 专属输出 Schema、业务终态 `PUSHED`、`WAITING_EXTERNAL`；普通 Push 仍是部署前必须核实的阶段 |
| 业务与界面   | 外部部署成功／失败报告、其附件入口和时间线、等待外部结果的展示与操作                             |
| 数据结构     | 外部部署报告表及附件关系、重试关联报告外键、状态 CHECK 和活动批次索引中的旧枚举                  |
| Skill 与测试 | XUpdate 的 CI/CD 分支，相关测试夹具及浏览器场景；保留审批、问答、会话同步与本地脚本失败恢复      |

工程配置更新的现有权限及活动提测引用保护继续适用。不能通过直接修改数据库制造可编辑场景，再把测试构造误述为当前产品行为。

## 实施顺序与验证

1. 先收敛全局部署契约及状态：字段、表单、业务结果、数据库与 XUpdate 同步改为脚本部署，保证 AgentParty 的既有分工流程完整可用。
2. 扩展通用 Execution、工作区组和逐仓库结果校验；单工程场景也通过同一集合协议运行。
3. 接入模式与 PersonAgent 范围解析、Bug 修复、串行调度及跨工程批次，再接页面投影和返修。
4. 完成跨 Web/xapt 的协议与状态回归，以及隔离双仓库的真实 Codex 验收，最后处理切换。中间提交不等于可部署的完整版本，不保留长期半兼容状态。

验收必须覆盖：排队期间追加工程、运行中追加不改变快照、原会话返修加入新工程、两仓库提交不可串用、单端无改动、批次冻结与后续候选、后端成功前端失败、Push 或部署结果丢失后的恢复、自动串行与更新并行、人工交接及工作区清理，以及 AgentParty 关联 Bug 的现有回归。

实际验证入口以实施时的影响面为准，已存在的总质量门包括 `bun test`、`bun run typecheck`、`bun run format:check`、`bun run build:app` 和 `bun run test:browser`。模块职责调整另核对 `bun test apps/web/server/architectureBoundaries.test.ts`；新增文件运行 `bun test scripts/fileNaming.test.ts`。浏览器验收沿用用户指定的 Dia 连接。真实会话验收使用隔离仓库和假远端／假部署目标，不能把本设计文档或 Fake Codex 测试当作真实执行通过。

## 切换与证据边界

现有数据库为 Schema 32，未来需要新 Schema；本设计不执行迁移或清空数据。既有提测保留并归为 AgentParty；旧 CI/CD 配置可能没有真实命令，历史 `PUSHED` 不能改写为脚本部署完成。本机历史数据已作下述只读预检，实施前仍须重新核对当时状态，再确定离线转换和旧会话处置。

`x-skills` 的 XBugRepaire 与 XUpdate 位于独立仓库，当前均按单工作区描述执行。同一 Task 固定 Skill Bundle，不能只升级入口软链接就假定旧会话获得新契约。Server、xapt、两个 Skill 及其已有任务需要作为一个切换组合验证；不在目标工程内复制 Skill 或修改用户全局 Codex 配置。

目标前端工程现有 `scripts/buildTest.js` 还需同步补齐缓存位置参数的匹配规则和周期维护入口；不能仅改 xapt 的 worktree 准备就认为产物复用与清理已经生效。该工程脚本本轮只读核实和隔离诊断，尚未修改。

本轮已核对当前源码并刷新 GitNexus 索引。`environmentDeploymentSettings` 的图中影响为 2 个直接调用方、1 个流程分组；`ExecutionPreparation.prepare` 为 1 个直接调用方、1 个流程分组；`executionsConflict` 为 4 个直接调用方、2 个流程分组。图对 Schema 引用和 `updateService().reportExternalDeployment(...)` 这样的调用存在漏报，因此不能据其 LOW 或零调用方结果判定整体改造低风险；契约、状态机和数据切换必须以源码及真实回归补足。实际修改函数前仍需按最终目标逐个运行影响分析。
