# 先复用修复上下文，再设计验证结果复用

Repair 到 Update 的优化首先补齐跨会话上下文，并依据实际检查覆盖关系合并同轮重复命令；历史验证通过结果的自动复用作为后续独立能力。已有验证摘要用于理解先前工作，第一版仍满足当前工程对本阶段的验收要求，避免把上下文交接误当成免检凭据。

沿用 [ADR-0001](0001-keep-runner-domain-neutral.md) 的执行边界：Cooking 负责业务交接，Codex 按 Skill 执行，xapt 提供通用运行能力。稳定流程继续由 `x-skills` 提供，结构化输入输出由本工程定义；本次优化不修改目标工程的 `AGENTS.md`。

以修复到交付的总成本衡量优化效果：Repair 满足修复验收，Update 对选中的最终组合补齐交付验收，不为缩短 Update 的显示耗时而要求每次 Repair 提前执行全部发布检查。保留两阶段职责，接受第一版仍可能重跑跨阶段检查，以控制证据有效性判断的复杂度。

## 交接归属与内容

Repair Handoff 关联产生候选提交的来源 Repair Attempt 和提交，随 Update Batch 一起冻结。同一 Bug 的候选可能累积自多次成功修复，应保留各次交接与其提交的关系；后续会话的新结论不替换既有批次的交接，单次修复的验证结论也不扩展为整个组合的验证结论。

交接采用精简的结构化摘要，复用已有修改、验证和警告信息，补充已用验证入口与必要参数、已验证的环境解决办法、影响范围与关键入口、未验证或未完成事项，以及结论适用条件和限制。不默认加载完整聊天或日志；命令是需要结合当前仓库核实的历史线索，本机绝对路径与敏感环境值不进入 Server 交接数据。具体字段契约仍待设计。

## 更新执行顺序

Update 先核实交接、当前仓库规则、必要工具和 Git 状态，再集成全部冻结候选，对最终组合制定并执行一次验收计划；根据实际覆盖关系合并能共同完成的命令。冲突在集成时处理，验收后的代码或输入变化触发受影响部分的重验；远端状态与推送结果始终现场核验。这样减少逐个候选重复完整构建，同时保留对最终交付状态的验证责任。
