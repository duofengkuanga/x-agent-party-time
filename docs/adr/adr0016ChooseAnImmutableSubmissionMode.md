# 在提测创建时选择固定的协作模式

PersonAgent 预期成为高频使用方式：一名开发负责人通过一个 Agent 同时处理参与工程，由另一名测试负责人验收。保留现有按工程分工的流程为 AgentParty，避免统一跨工程处理取代仍有需要的分工协作；两种模式的领域定义见根目录 [CONTEXT.md](../../CONTEXT.md)。

新建提测默认选中 PersonAgent，创建前明确展示所选模式以及创建后不可更改的约束。模式属于本次提测，不由人数、电脑数或 Agent 数量自动推断；现有提测归为 AgentParty，继续原有工程分工流程。两种模式的部署统一遵循 [ADR-0017](adr0017UseDeploymentScriptsForEveryEngineering.md)。

PersonAgent 登记 Bug 时不要求测试判断前后端。一条 Bug 始终保留一个持续修复会话，即使涉及多个工程也不拆成多条 Bug；内部记录各工程的修改与交付进度，相关工程全部就绪后统一验收，返修继续原 Bug 的原会话。AgentParty 继续使用 [ADR-0012](adr0012SplitCrossEngineeringReportsIntoLinkedBugs.md) 的工程归属与关联 Bug 规则。

## 提测范围与修复入口

PersonAgent 使用平台现有的 Project 和 Engineering 配置。创建提测时统一选择开发负责人和 Agent，再确定参与工程及各自的目标分支、测试环境；本机 Agent 根据已有 Binding 解析目录，不以 Codex 桌面项目的文件夹配置决定修复范围。登记 Bug 时自动使用本次提测的工程上下文，不再要求测试选择目录或工程归属。

PersonAgent 在提测过程中允许追加参与工程，仍须满足同一开发负责人、同一 Agent 的约束；本次不提供移除工程的能力。追加工程不改变协作模式创建后不可切换的规则。

每轮自动修复开始时确定本轮参与工程范围，执行中保持不变。追加工程后，已经排队但尚未开始的 Bug 在开始时使用最新范围；旧 Bug 后续返修继续使用原会话，并纳入新增工程。当前正在执行的修复保持原范围，已冻结的更新批次也保持不变。

各工程的目标分支在该工程首次进入自动修复范围时锁定；此前开发负责人可以更正分支选择。追加工程独立判断锁定时点。锁定约束的是目标分支配置，不阻止该分支正常接收新提交。

保留现有的“仅登记 Bug”和“登记 Bug 并修复”两个入口。仅登记时等待后续修复请求；登记并修复时进入执行队列，指定 Agent 离线时等待上线领取。进入队列与实际开始修复分别展示，不把登记成功或入队成功描述为已经开始执行。

修复会话在本次参与工程内连续完成调查、修改、验证和本地修复提交，不新增诊断完成后的人工批准关卡。资料不足、预期行为有歧义或需要修改范围外工程时暂停澄清；跨工程 Push、部署与恢复属于后续 Update 阶段，本项决定不将其自动包含在 Repair 授权中。

## 修复与更新调度

同一张 PersonAgent 提测单内，多条 Bug 的自动修复串行排队，各自保留独立会话。已修好的 Bug 可以进入更新流程，不等待该提测单的全部 Bug 修复完成。

Repair 与 Update 可以并行执行：例如 A、B 已修好并冻结为更新批次，该批集成和部署期间可以继续修复 C。串行限制针对多条 Bug 的自动修复，不将修复与更新合并为一条串行队列。

PersonAgent 任一参与工程失去测试环境占用时，整张提测单暂停更新和验收，修复仍可继续。重新取得所需环境并确认环境版本正确后恢复交付与验收。AgentParty 保留既有按工程处理环境占用的规则。

## 人工等待保留现有设计

人工等待改造移出本次 PersonAgent 范围，继续沿用 [ADR-0013](adr0013HandOffAsynchronousConfirmations.md)：已有同步审批和问答仍使用平台 Interaction；异步问题仍交给开发负责人在原 Codex 会话中处理，完成后回平台同步。不新增 hook 接入，也不新增异步问题的网页回答与托管续接流程。

人工交接继续保护原会话、原工作区及其清理，允许其他独立工作区任务继续，不增加等待人工期间的提测级独占。自动修复的串行约束不扩展到用户在平台外手动续接的会话；手动处理与其他自动修复仍可能重叠。后续若调整人工等待与恢复调度，再单独重新设计该边界。

## 统一更新批次与部署

PersonAgent 按同一张 Test Submission 收集已修好的待更新 Bug，统一组织跨工程 Update Batch，不再按前后端分别组织更新批次。保留末次产生新候选后等待五分钟自动更新及“立即更新”入口，计时和操作范围改为该提测单；冻结时仍在修复的 Bug 留待后续批次，不因其未完成而阻止当前批次。

工程配置统一只填写部署脚本，PersonAgent 和 AgentParty 均不再提供 CI/CD 部署模式或外部流水线结果确认，见 ADR-0017。PersonAgent 两端都有改动时默认先部署后端，确认成功后再部署前端；后端部署失败则停止后续部署。只有一端有改动时仅部署该端。

整个批次全部部署成功后，该批全部 Bug 统一进入待验证。某端部署失败时，即使部分 Bug 只涉及已成功部署的工程，也仍随批次等待，测试不对该批进行部分验收。

跨工程统一安排更新不代表多个仓库的 Push 或部署具有事务原子性。部分部署成功时保留已成功部署的版本，不自动回滚；开发负责人处理失败原因后重试。重试先核实各工程的实际 Git、Push 和部署状态，再继续未完成的步骤；状态不明时先查证，不盲目重复已完成的部署。

## Considered Options

- 用跨工程统一处理全面替换现有流程：简化模式数量，但不能保留不同负责人、不同 Agent 的工程分工。
- 依据人数或 Agent 数量自动选择模式：现有流程也允许同一负责人、同一 Agent 负责多个工程，这些数量不能表达期望的处理方式。
- 允许活动提测切换模式：会改变已有 Bug、修复会话与交付记录的含义，因此模式在创建后固定。

## 实现状态

上述产品流程已由用户整体确认。本轮不修改业务实现；技术设计提案和待验证边界见 [PersonAgent 技术设计](../design/personAgentExecutionDesign.md)。模式不可变、PersonAgent 的负责人及 Agent 一致性、跨工程统一验收等约束的自动化检查均待实现。
