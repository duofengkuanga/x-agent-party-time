# 将跨工程缺陷登记拆分为关联 Bug，由人工决定后续流转

> 本文为已确认的设计，尚未实现。

测试负责人只填写一次缺陷资料；选择前端和后端工程时，系统生成两条相互关联、分别归属对应工程的 Bug。每条 Bug 独立修复、交付和验收，详情中展示关联 Bug 的进度，不增加需要维护汇总状态的父单，也不自动联动验收通过或返修。这保留了现有单工程修复与更新边界，代价是测试需要分别验收，并在完整功能依赖另一工程时等待其交付。

仅单工程处理的缺陷开放两个对称动作：转交前端／后端，以及增加前端／后端协作。执行转交时，系统自动关闭原 Bug，根据原始资料生成关联 Bug，并自动将新 Bug 放入修复队列；原 Bug 保留诊断依据和关闭原因，关闭不代表修复完成或验收通过，不另设“已转交”看板列或专用列表。增加协作同样生成关联 Bug，但保留原 Bug 继续处理，形成双工程处理。

## 操作规则

- 测试登记时选择前端＋后端，则拆出的两条 Bug 都不提供转交或增加协作；后续通过增加协作形成双工程处理时，同样关闭这两个入口。关联单完成或取消不重新开放入口，不引入关联单复用、重新打开或重复生成目标工程 Bug 的特殊流程。
- 测试负责人和原 Bug 的工程负责人可以阅读 Codex 实际返回的原始结果，自行决定转交或增加协作，不要求目标工程负责人二次确认。测试负责人必须能看到用于判断的实际结论和原因，不能仅展示修复成功或失败的标题。
- 不为分诊修改 Prompt、`x-skills` Repair Skill 或 Codex 结果 Schema，不要求 Codex 返回转交／协作分类、建议目标工程或动作专用字段，也不由平台从结果文本推断归属或自动流转。
- 转交和增加协作是独立的人工操作，是否开放由业务条件决定，不依赖 Codex 是否主动提出建议。双工程处理时页面不展示入口，服务端也不允许执行；不向 Codex 增加分诊能力开关或分诊任务。
- 转交和增加协作都必须等当前 Codex 任务结束后才能执行；转交还要求原 Bug 没有待交付改动。已完成、已取消、因转交关闭的 Bug 不发起这两个动作。
- 登记时拆分生成的 Bug 都进入待修复；处理过程中转交或增加协作新生成的 Bug 自动开始修复。新 Bug 携带原始资料、附件和已有 Codex 结果，保留人工操作来源，不要求 Codex 额外生成专用交接结果。
- 新单创建、关联与修复入队成功后，转交才关闭原单；操作应保持一致，失败不得留下原单已关闭但没有接续处理单的状态。重复点击或请求重试不得重复建单或重复入队。入队成功不等于 Codex 已开始执行或修复成功。
- 增加协作后，原 Bug 若尚需修复，由工程负责人根据关联单进展在原 Codex 会话中人工继续，再使用现有会话同步机制更新平台；不自动唤醒原会话或编排两端执行顺序。原工程已经修好时照常交付，由测试等待两端就绪后分别验收。

## Considered options

- 一条 Bug 同时归属多个工程：可统一验收，但需要改变现有修复会话、交付状态汇总和返修范围等规则。
- 测试手工登记两条 Bug：保留单工程流程，但重复填写资料，也容易丢失两条 Bug 的关联。
- Codex 返回结构化转交／协作建议：需要新增判断规则，并可能诱使模型过早结束修复；最终选择保持原有修复任务，由人工阅读实际结果后决定工程流转。

## Consequences

- 自动拆单减少重复登记，不承担跨工程接口协调、部署顺序或验收就绪判断。
- 转交关闭必须保留原因和新旧 Bug 关联，不能将关闭解释为问题已经解决。
- 落地范围为本工程的结果呈现、人工操作、关联 Bug 及业务状态，不包含 `x-skills` 或 Prompt 改造。原有修复结果校验与状态同步机制继续沿用。
