# 人工交互超时后让出 Bug 修复执行机会

Bug Repair 的权限审批和问答统一由平台收集答复并安排自动续接，包括此前按 [ADR-0013](adr0013HandOffAsynchronousConfirmations.md) 交给原 Codex 会话处理的异步问答。负责人可以在平台内回答，不再因这类交互被要求切换应用处理后手动同步结果。此决策调整 Repair 的交互方式，未扩展到 Update 等其他执行。

每个新的人工请求从平台首次记录时开始计算 60 秒等待窗口；页面刷新、断线与服务重启不重置同一请求的计时。窗口内收到答复即可继续当前执行；满 60 秒仍未收到答复时，Bug 保留问题、修复上下文与工作区，并让后续可执行 Bug 获得执行机会。多个 Bug 连续等待都能依次让位；让位后的等待项不占活动执行容量，不能因前两个 Bug 都等待人工处理而阻止第三个启动。等待不构成修复失败，也不表示用户已经同意权限请求。

收到答复只使 Bug 进入等待恢复的队列，不打断正在执行的 Bug。已答复任务优先于尚未启动的任务，多个恢复任务按答复先后排序。例如 Bug 3 正在运行，Bug 1、Bug 2 先后收到答复，则后续顺序为 Bug 3 → Bug 1 → Bug 2 → 尚未启动的 Bug 4；各任务实际恢复仍须满足执行条件。

恢复时沿用原 Codex Session 和工作区，允许在原会话中开启新 Turn，先核对现场再继续未完成的工作。保留上下文不等于原进程、原 Turn 或原工具请求能够原样恢复，也不表示从头重做修复。权限批准仅对应原请求；恢复后操作的目标、内容或权限范围发生变化时，必须重新确认，不能将之前的批准扩大到新请求。

拒绝权限也是有效答复，遵循相同的恢复顺序。Agent 收到拒绝结果后可以选择不需要该权限的方案；拒绝单项权限不直接等于取消整个 Bug，也不得把拒绝当成批准。

人工等待不设自动失效时限。即使一天没有答复，也保留问题、上下文与队列状态，不因等待自动失败、取消或从头重跑。服务重启后继续保留原请求、计时起点、已保存的答复与恢复排序依据；如果原会话无法继续，明确提示需要人工处理，不静默创建新的修复会话替代。

长期保留仍受现有处理权限、业务状态和 Execution 取消约束。旧请求失效后不能凭旧答复重新恢复任务；长期等待不构成扩大答复权限或绕过状态校验的理由。

这个选择避免人工响应速度阻塞整条修复队列，并让已投入工作、已得到答复的 Bug 优先继续。代价是平台需要同时保存多个等待项，明确区分等待人工、等待恢复与正在执行，并在 Server 和本机 xapt 两端协调执行资格及原会话、工作区的保护。它不同于将会话控制权交给负责人在平台外继续处理的 Manual Session Handoff。

## 主动结束等待

测试负责人可以取消等待人工或等待恢复的 Bug，沿用原有取消权限并扩展可取消状态。取消后 Bug 移出恢复队列，原人工请求及已保存答复不再允许触发恢复，迟到的答复也不能重新启动修复；已有处理记录保留。此入口让负责人可以主动结束长期无人处理的等待，不必先批准权限或回答问题。

取消及恢复执行须核对实际状态，不能因网页仍显示等待而取消一个已经恢复运行的任务。后续显式恢复已取消 Bug 时沿用既有业务流程，不重新启用旧确认。提测关闭仍须满足原有完成条件，不能通过关闭操作强行结束尚未停止的执行。

## 实施与验证边界

Repair 通过通用 Execution 的托管交互策略实现上述行为。异步问题完整保留选项并在原 Session 开启新 Turn 消费答复；本机释放回执经持久化与进程退出确认后才解除调度占用。Update 保留原人工接管及部署进程生命周期，不采用 Repair 的进程组收敛。

验证包括可控时间的队列测试、公开 Agent 协议与业务入口、真实 Codex 原会话续接、真实隔离子进程，以及页面角色和错误状态。覆盖连续让位、原答复排序、不抢占、回执重试与幂等、拒绝权限、上下文保留、长期等待和重启恢复、取消与恢复竞争、迟到答复失效和提测关闭约束。接口类型或模拟执行器不能替代真实会话与进程验证；入口见 [README](../../README.md#人工交互与修复队列)。

本机进程归属记录在初始化前落盘，受控退出确认后清除。释放失败继续保留执行与恢复阻塞；异常退出导致归属不明时，不把根进程消失当作工具已退出的证明。此类故障需要工程负责人按 README 的维护流程核验，不自动删除锁、清空回执或重建会话。
